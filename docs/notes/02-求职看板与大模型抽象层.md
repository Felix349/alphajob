# 设计笔记 02：求职看板与大模型抽象层

> W2 ｜ 涉及文件：`backend/app/models/application.py`、`backend/app/llm/`、`backend/app/services/applications.py`、`frontend/src/components/board/board.tsx`、`frontend/src/hooks/use-applications.ts`

## 1. 数据模型

```
User 1 ──< Application（投递记录）1 ──< Event（日程：笔试 / 面试 / 截止）
              │
              └── jd_parsed（JSONB）：大模型解析出的结构化 JD，W3 岗位匹配会用到
```

### 阶段为什么只有 7 个，一面、二面不单独占一列？
看板的列越多，越难一眼看清全局。"一面/二面/三面"本质上是**同一阶段里的多场事件**，所以用 `Event` 记录，卡片上显示"下一场"。真正改变一个投递状态的只有：待投递 → 已投递 → 笔试 → 面试中 → HR 面 → Offer / 已结束。

### Event 为什么冗余存一份 user_id？
日历视图要按时间范围查询"我的所有日程"。如果只存 `application_id`，每次都要 join 投递表来过滤用户。冗余一列 `user_id` 后，查询更简单，**权限过滤也更直接**：所有查询都带 `WHERE user_id = 当前用户`。这是一个用存储换简单和安全的取舍。

### 枚举为什么用 `native_enum=False`？
PostgreSQL 原生的 ENUM 类型，加新值需要 `ALTER TYPE`，而且删值很麻烦。存成 varchar，由 Pydantic 校验，以后加阶段只需要改代码。

## 2. 拖拽排序：浮点数 position

**问题：** 卡片在一列里的顺序要持久化。如果用 0、1、2、3 这样的整数，把卡片插到中间时，后面的卡片都要 +1，一次拖拽要更新整列。

**做法：** position 用浮点数，间隔 1024。
- 新卡片放在最上方：`min(position) - 1024`
- 拖到 A、B 之间：`(A.position + B.position) / 2`
- 每次拖拽**只更新被拖的那一张卡片**

**代价：** 在同一个位置反复插入约 50 次后，浮点精度会用完。到时可以做一次"重新编号"，个人求职场景基本遇不到。（Trello、Linear 用的是类似思路；Figma 用的是字符串版本的 fractional indexing。）

### 乐观更新
拖拽松手后，**先改界面、再发请求**（TanStack Query 的 `onMutate`）。请求失败就回滚到修改前的数据，并弹出提示。这样拖拽没有任何延迟感。

## 3. 大模型抽象层

```
业务代码（services/jd.py）
      │ 只依赖 LLMClient 接口：structured(system, user, schema, effort)
      ▼
┌──────────────────────────┐    ┌──────────────────────┐
│ OpenAICompatibleClient   │    │ AnthropicClient      │
│ DeepSeek / 通义 / OpenAI │    │ Claude（官方 SDK）    │
└──────────────────────────┘    └──────────────────────┘
      ▲ 由配置 LLM_PROVIDER 决定用哪个（factory.py）
```

### 两家的结构化输出为什么实现方式不同？
| | OpenAI 兼容接口（DeepSeek） | Claude |
|---|---|---|
| 服务端能力 | DeepSeek 只支持 `json_object`（保证是 JSON，但不保证字段对） | 支持按 JSON Schema 约束生成 |
| 我的做法 | 在提示词里给出 Schema，用 Pydantic 校验；**校验失败就把错误发回给模型让它修正**，最多重试 2 次 | 直接用 SDK 的 `messages.parse(output_format=PydanticModel)`，返回校验好的对象 |

这就是"抽象层"的价值：业务代码不需要知道这些差异。

### 为什么不用 LangChain / LiteLLM？
自己写的适配器只有一百多行，每一步都看得见、能调试。而且这部分正好是我的专业方向，面试时能讲清楚各家接口的差异。等需要支持十几家模型时，再考虑引入 LiteLLM。

### 其他细节
- **Pydantic 模型就是提示词：** `ParsedJD` 每个字段的 `description` 会进入 JSON Schema，模型会读到它。字段描述写得越清楚，提取得越准。
- **用 XML 标签包裹 JD 原文：** 让模型区分"指令"和"数据"，也能降低 JD 里夹带的文字被当成指令执行的风险（提示词注入）。
- **effort="low"：** 信息提取不需要深度推理，Claude 用低 effort 更快、更便宜。
- **每次调用都写入日志：** `LLMCallLog` 记录功能、模型、token 用量、耗时、成败，为后面的成本统计打基础。
- **大模型只负责"填表"：** 解析结果先展示给用户确认、修改，用户点保存才入库。模型出错不会直接污染数据。
- **没有配置 Key 时优雅降级：** 接口返回 503，前端提示后自动进入手动填写，不阻塞主流程。

## 4. 测试策略

- **业务接口（17 个用例）：** 增删改查、阶段变化时的自动规则、日程时间校验、日历范围查询，以及一个专门的**越权测试**（用户 B 对用户 A 的投递和日程做查、改、删，全部返回 404，并确认 A 的数据完好）。
- **大模型（9 个用例）：** 全部用假实现，不发真实请求。覆盖：结果和日志写入、失败时返回 502 并记录错误、根据配置选择适配器、**JSON 修复重试**（第一次缺字段、第二次正确）、多次失败后放弃、输出被截断。
- **真实模型评估（`scripts/eval_parse_jd.py`）：** 10 条虚构用例，覆盖规整格式、实习、没有公司名、只写月日、日期已过、全英文、只有产品名、网页杂乱复制、提示词注入、软技能干扰。2026-11-04 的结果：

  | 模型 | 运行次数 | 字段准确率 | 平均耗时 |
  |---|---|---|---|
  | deepseek-chat | 10 条 × 1 次 | 82/82 = 100% | 1.5 s |
  | deepseek-flash | 10 条 × 3 次 | 246/246 = 100% | 2.1 s |

  单条解析大约消耗 1000 个输入 token、150–400 个输出 token。
- **真实 JD 评估（33 条，本地，不提交）：** 来自 DeepSeek（6 条）、华为（18 条）、小米（5 条）、腾讯（4 条）的真实校招 JD。
  - **真实 JD 大多不写公司名：** 腾讯只写事业群（CSIG、WXG……），华为、小米多数只有岗位标题。按产品决定，公司和岗位以招聘页标题为准：评估时把标题作为第一行放进正文，模拟用户连同标题一起复制的情况。
  - **陷阱：** 华为每条都有“更新于 2026-08-17”，这不是截止日期；腾讯的“参加面试的城市”不是工作地点；小米的 Agent 产品经理 JD 里提到了 OpenAI、Anthropic 等竞品，不能被识别成公司。
  - **结果（deepseek-flash，2026-11-04）：** 10 条虚构 + 33 条真实，**309/309 = 100%**；平均耗时 4.0 秒，长 JD（DeepSeek 的 8–12 KB）要 6–7 秒；平均每条约 1400 个输入 token、750 个输出 token。
- **评估还没覆盖到的问题（抽查原始输出时发现）：**
  1. **技术栈的精确率：** 评估只检查“该有的技术有没有”（召回），没检查“不该有的有没有混进来”。实际输出里会出现“大模型”“AI Agent”“Profiling 工具”这类不是具体技术的词。
  2. **条数上限没被遵守：** Schema 写了“最多 8 条”，但有的输出列了 9 条职责。描述里的限制对模型只是建议，需要时应在 Pydantic 里用 `max_length` 硬性约束，或在后处理中截断。
  3. **用例都是校招岗：** 社招、英文 JD 的真实样本还很少。

## 5. 踩过的坑

0. **提示词里的"今年"：** 最初的提示词写着"只写了月日时，按今年计算"，但模型并不知道今天是哪一天。改成在用户消息里传入今天的日期，并说明"已经过去的月日算作明年"。评估集里有两条用例专门测这一点。日期放在用户消息而不是系统提示词里，是为了让系统提示词保持不变、能命中缓存。

1. **Next.js 16 的 cacheComponents：** 动态路由里，客户端组件调用 `usePathname()` / `useParams()`，或者渲染时调用 `new Date()`，都必须包在 `<Suspense>` 里，否则会阻塞预渲染。解决：把侧边栏导航、详情页、日历分别包进 Suspense。
2. **FullCalendar v7 改了包结构：** 插件从独立的 `@fullcalendar/daygrid` 合并进了 `@fullcalendar/react/daygrid`，混装 v6 和 v7 的包会出问题。
3. **Google Fonts 在国内加载失败：** `next/font/google` 在开发时要下载字体，网络不通就报错。改用 `geist` npm 包，字体文件随项目打包。
4. **React 的纯函数规则：** 渲染函数里不能直接调用 `Date.now()`（结果不稳定），lint 会报错。改成 `useState(() => Date.now())`，只在首次渲染时取一次。
