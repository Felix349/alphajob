# 设计笔记 04：面试复盘、语音转写与后台任务

> W4 ｜ 涉及文件：`backend/app/services/interview_pipeline.py`（处理流程）、`backend/app/tasks.py`（任务队列）、`backend/app/worker.py`（Worker 入口）、`backend/app/asr/`（语音转写）、`frontend/src/components/interviews/`

## 1. 功能流程

```
面试结束 → 口述录音 / 上传录音 / 写文字
        → POST /api/applications/{id}/interviews（立即返回，状态 pending）
        → 任务进入 Redis 队列
Worker  → 转写（只有语音） → 大模型整理与评估 → 写入题库和薄弱点 → done
前端    → 每 2 秒轮询状态，处理完成后自动停止
```

## 2. 为什么需要后台任务

转写加分析要 30 秒到几分钟。如果在 HTTP 请求里同步处理：
- 用户要一直等着，关掉页面就前功尽弃
- 服务重启时，处理到一半的任务直接丢失
- 慢任务会占住 Web 服务的并发能力

改成后台任务后：**请求只负责“保存数据 + 把任务放进队列”，立即返回**；真正的处理交给独立的 Worker 进程。

```
API 进程 ──enqueue──> Redis ──取任务──> Worker 进程
   ↑                                      │
   └────── 前端轮询状态 ←── 数据库 ←──────┘
```

### 为什么选 ARQ
- 原生 asyncio，和 FastAPI、SQLAlchemy 异步的写法一致
- 比 Celery 轻量得多，一个类就能配置好
- Redis 本来就在技术栈里

### 状态机
```
pending ──语音──> transcribing ──> analyzing ──> done
   └──────文字───────────────────────┘
任何一步出错 → failed（记录原因，用户点“重试”）
```
- **每一步都立刻提交数据库**：前端轮询时才能看到实时进度
- **幂等**：任务被重复执行时，先删掉这场复盘的旧题目再写入，题库不会出现重复
- **重试时跳过已完成的步骤**：已经有转写结果就不再转写，不重复花钱
- **不自动重试**（`max_tries=1`）：API Key 失效这类问题自动重试也没用，只会白白消耗额度。失败原因写进数据库，由用户决定
- **卡死检测**：处理中的状态超过 15 分钟没变化，视为 Worker 中途挂了，允许用户手动重试
- **Redis 没启动时**：数据照常保存，状态标为失败并提示“后台任务服务不可用”，恢复后点重试即可

### 测试怎么办
业务代码只依赖 `TaskQueue` 接口。测试时换成“入队即执行”的 `InlineQueue`，不需要启动 Redis 和 Worker，测试照样能覆盖完整的状态机。

## 3. 语音转写

### 模型选择：paraformer-realtime-v2
调研了阿里云百炼的几类语音识别接口：

| 类型 | 代表模型 | 能否直接用本地文件 | 时长上限 |
|---|---|---|---|
| 录音文件识别 | paraformer-v2、fun-asr | ❌ 必须是公网 URL | 12 小时 |
| 一句话识别 | qwen3-asr-flash | ✅ Base64 | **5 分钟 / 10 MB** |
| 实时识别 | **paraformer-realtime-v2** | ✅ SDK 直接读文件 | **不限** |

口述回忆经常超过 5 分钟，而本地部署又没有公网 URL，所以选了实时识别模型。它的限制是**支持的格式少**：浏览器录音的 webm、手机录音的 m4a 都不支持。

### 解决格式问题：统一转成 16 kHz 单声道 WAV
用 ffmpeg 把任何格式都转成语音识别最标准的输入格式。ffmpeg 来自 `imageio-ffmpeg` 这个 Python 包，它自带二进制文件，**不需要在系统里另外安装**，CI 和 Docker 里也能直接用。

转换时顺便做了几件事：丢掉视频轨（有人会上传录屏）、只转前 30 分钟多一点（足够判断是否超限，不会白白处理几小时的文件）、太短（不到 1 秒）直接拒绝。

### 阻塞操作放进线程
ffmpeg 转换和 SDK 识别都是同步阻塞的，用 `asyncio.to_thread` 放到线程里执行，不卡住 Worker 的事件循环（Worker 同时可能在处理其他任务）。

## 4. 复盘分析的提示词要点

- **语音转写会把技术名词写错**：比如“瑞迪斯”其实是 Redis。提示词要求按上下文纠正
- **防编造**：回忆里没提到怎么答的，“当时的回答”必须填 null
- **追问也算一道单独的题**，不要把不同的问题合并
- **薄弱点要具体到知识点**：要“Agent 评测方法”，不要“技术深度不够”
- **参考回答按口头回答的方式组织**：先结论，再分点展开

## 5. 前端

- **浏览器录音**：用 MediaRecorder 录成 webm（Chrome、Edge）或 mp4（Safari），每秒产出一块数据，中途出问题也不会全部丢失。后端统一转码，前端不用关心编码细节
- **轮询而不是 WebSocket**：任务只持续几十秒到几分钟，每 2 秒查一次状态就够了；处理完成后，TanStack Query 的 `refetchInterval` 返回 `false`，自动停止轮询
- **进度步骤条**：根据状态和“有没有转写结果”判断卡在哪一步，失败时在对应步骤上标红，并给出重试按钮
- **题库**：没掌握、分数低的题排在最前面；筛选项从“全部题目”里统计，选了一个公司之后，其他公司的选项不会消失

## 6. 数据模型

```
Interview（一场复盘）1 ──< Question（一道题，进入个人题库）
         │           └──< WeakPoint（薄弱点，W6 的 Agent 会读取）
         └── summary（JSONB：总结、亮点、下一轮建议）
```
逐题结果单独存表（而不是塞在 summary 里），因为题库需要按公司、标签、掌握程度跨面试检索。标签存成 JSONB 数组，用 `tags @> '["缓存"]'` 做包含查询。

## 7. 验证结果（2026-11-05）

- **自动化测试**：后端 77 个，比 W3 多 17 个。覆盖文字和语音两种输入、转写失败、分析失败、重试时跳过已完成的步骤、Redis 不可用、重复执行不产生重复题目、输入校验、越权访问、删除时同时删除录音文件、题库筛选和排序、路径穿越防护，以及**真实运行 ffmpeg** 的格式转换测试
- **端到端冒烟测试**：用 Windows 自带的中文语音合成生成一段模拟口述，转成 webm 格式，然后走**真实 Redis 队列 + 真实 Worker + 阿里云转写 + DeepSeek 分析**：
  - 32 秒的录音，转写约 7 秒，分析约 12 秒
  - 整理出 4 道题，评分合理；薄弱点准确（Agent 记忆淘汰策略、Agent 评测方法、项目表达深度）
- **已知小问题**：“自我介绍”这类回忆里没写具体内容的题，参考回答里会出现一点回忆之外的内容（比如“熟悉 Python 后端开发”）。之后收紧提示词

## 8. 踩过的坑

1. **ARQ 在 Windows 上退出时报错**：关闭时会调用 `handle_sig(signal.SIGUSR1)`，而 Windows 没有 `SIGUSR1`（任务本身已经正常完成）。在 `worker.py` 里把它映射成 Windows 上存在的 `SIGTERM`，只在 Windows 上生效。
2. **空的表单字段被当成“缺失”**：FastAPI 会把空字符串的 Form 字段当成没传，直接返回英文的“Field required”，轮到不了业务层的中文提示。解决：给字段设默认值空字符串，交给业务层校验。
3. **录音文件识别类模型要求公网 URL**：本地开发环境没有公网 URL，官方的临时上传方式又注明“不适合生产环境”，所以换成了能读本地文件的实时识别模型。
