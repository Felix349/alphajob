# 设计笔记 05：求职 Agent

> W6 ｜ 涉及文件：`backend/app/agent/`（工具、循环、写操作确认）、`backend/app/llm/*`（`tool_session`）、`backend/app/services/plan.py`（计划）、`frontend/src/components/agent/`

## 1. 两种工作模式

| | 今日 / 本周计划 | 对话 |
|---|---|---|
| 上下文怎么来 | **代码确定性地收集**：近期日程、进行中的投递、未完成的备考项、未解决的薄弱点、面完还没复盘的场次、待复习的题 | **模型自己调用工具**按需查询 |
| 调用模型的次数 | 1 次（结构化输出） | 1–8 次（工具调用循环） |
| 为什么这样选 | 需要的数据是固定的几类，一次给齐更稳定、更便宜、更好测试 | 问题五花八门，没法提前知道要查什么 |

一个好的 Agent 设计不是“所有事都让模型自己决定”。**能用代码确定的就用代码，只把真正需要判断的部分交给模型。**

## 2. 工具调用循环（不用框架，约 100 行）

```
用户消息 ──> 模型 ──有工具调用?──否──> 最终回答，结束
              ↑          │是
              │          ↓
              └── 工具结果 <── 执行每个工具（读工具直接执行；写工具生成“待确认操作”）
```

- **最多 8 步**：防止模型陷入“反复调用工具”的死循环
- **错误交还给模型，而不是中断对话**：未知工具、参数校验失败、id 不存在，都作为 `is_error` 的结果返回，模型通常会换个参数再试一次
- **工具结果截断到 8000 字**，避免挤占上下文
- **每一步都通过 SSE 推给前端**：thinking（模型的过渡语）、tool_call、tool_result、proposal、message，用户能看到“它调用了什么、依据是什么”

### 屏蔽两家模型的差异：`ToolSession`
各家的消息格式差别很大，所以抽象层提供的不是“发一次请求”，而是“一段工具对话”：

| | DeepSeek（OpenAI 兼容） | Claude |
|---|---|---|
| 工具定义 | `{"type": "function", "function": {name, description, parameters}}` | `{name, description, input_schema}` |
| 回传结果 | 每个结果一条 `role=tool` 的消息 | 同一轮所有结果放进**一条** user 消息的 `tool_result` 块 |
| 特殊要求 | 参数是 JSON 字符串，可能解析失败 | 助手回复的 content 要**原样**回传（里面有思考块） |

每个适配器用自己的原生格式保存历史，Agent 循环只需要反复调用 `step()` 和 `add_tool_results()`。

### 工具怎么定义
一个工具 = Pydantic 参数模型 + 用途说明 + 执行函数。JSON Schema 由参数模型自动生成，**同一个模型既校验参数，又告诉模型怎么调用**。用途说明是写给模型看的提示词，比如在 `list_applications` 的说明里写“回答任何关于投递的问题前，先用它拿到投递的 id”，模型就会先查再改。

## 3. 写操作：只能“提议”，确认后才执行

这是整个 Agent 最重要的安全设计。

```
模型调用写工具 → describe() 校验参数（数据存在、属于当前用户）并生成确认文案
             → 存一条 pending 的 AgentAction → 前端显示“待确认”卡片
             → 告诉模型“等待用户确认”（模型据此回答“我准备了……，请确认”）
用户点确认   → 重新校验参数 → 执行 → done / failed
```

- **模型理解错了也不会弄乱数据**：最坏情况只是多一张被取消的卡片
- **确认文案由代码生成**，不是模型写的，用户看到的就是真正会执行的内容：“把「北辰云 · Agent 开发工程师」的阶段从‘面试中’改为‘HR 面’”
- **提议时就校验归属**：别人的数据对模型来说“不存在”，连提议都生成不了
- **执行时再校验一次**：从提议到确认之间，数据可能已被删除，此时标记为 failed 并告诉用户，而不是报 500
- **防重复执行**：只有 pending 状态能确认，重复点击返回 409

## 4. 时间与时区

- 前端把浏览器时区（如 `Asia/Shanghai`）随请求发给后端，系统提示词里写明“现在是 2026-11-05 22:28，星期四”
- 工具返回的时间统一转成用户本地时间的易读格式（`11-07 周六 14:00`），模型和用户看到的是同一种格式
- 模型给出的时间不带时区时，按用户本地时间理解
- Windows 上的 Python 没有时区数据库，需要安装 `tzdata` 包

## 5. 计划

- **今日计划**：3–6 件事，每件都要写理由，而且**理由必须引用具体数据**（哪场面试、哪个备考项、哪个薄弱点）
- **本周计划**：先排定死的节点，再倒推每天的准备
- **模型给的 application_id 不可信**：只保留真的属于当前用户的，其他置空
- **按天 / 按周缓存**：同一天打开页面不重新生成；过了这一天自动失效
- **记录哪些计划项被完成**：PRD 的成功指标之一是“计划被采纳的比例 ≥ 50%”
- **“面完还没复盘”的判断**：过去 3 天内的面试日程，且之后没有新建复盘记录

## 6. 验证结果（2026-11-05，deepseek-flash）

用模拟数据（2 天后有一场二面、昨天面完一场还没复盘、两个备考项、一个薄弱点）实测：

- **今日计划**：优先级完全正确，P1 是二面的备考项和对应的薄弱点，P2 是复盘昨天的面试，P3 是补全待投递的岗位；每条理由都引用了具体数据
- **“这周有哪些面试”**：调用 `list_events`，准确列出 2 场
- **“改成 HR 面”**：先查投递，再生成待确认操作；确认前阶段没变，确认后才改；还主动指出“日程里的二面时间和‘已经面过’对不上”
- **“下周三下午三点”**：正确换算成 11-11（周三）15:00
- **耗时**：计划约 6 秒；对话每轮 3–5 秒（2–3 次工具调用）

## 7. 踩过的坑

1. **事件辅助函数的参数名冲突**：`_event(name, **data)` 和事件数据里的 `name` 字段（工具名）冲突。改成仅限位置参数 `_event(kind, /, **data)`。
2. **rollback 之后对象过期**：执行写操作失败、rollback 之后，再读 `ctx.user.id` 会触发同步懒加载，异步 SQLAlchemy 会报 `MissingGreenlet`。解决：rollback 之前先把 id 存到局部变量。
3. **模型在确认前就说“已添加”**：提示词里只写了“不要说已经改好了”还不够，改成给出正面句式“我准备了……，请在下方确认”，并明确列出禁用词。
4. **浏览器实测发现：`useEffect` 返回了 Promise**：`useEffect(() => ref.current?.scrollIntoView(...))` 没有花括号，会把 `scrollIntoView` 的返回值当成 effect 的返回值。以前它返回 `undefined` 所以没问题，新版浏览器的滚动方法改为返回 Promise，React 把它当清理函数调用，报 “destroy is not a function”。教训：effect 里只做副作用时一律写花括号，不要依赖“返回值恰好是 undefined”。
5. **JSONB 列原地修改不会被检测到**：`plan.done_items.append(1)` 不会触发更新，要重新赋值整个列表。
