# 设计笔记 01：认证链路

> W1 ｜ 涉及文件：`backend/app/core/security.py`、`backend/app/api/auth.py`、`backend/app/api/deps.py`、`frontend/src/proxy.ts`、`frontend/src/components/layout/app-shell.tsx`

## 1. 整体流程

```
注册 / 登录
  浏览器 ──POST /api/auth/login──> Next.js ──转发──> FastAPI
                                                    │ 1. 校验邮箱 + 密码（argon2）
                                                    │ 2. 签发 JWT（sub=用户 id，exp=7 天）
  浏览器 <──Set-Cookie: alphajob_token=<JWT>; HttpOnly; SameSite=Lax──┘

之后的每个请求
  浏览器 ──自动带上 Cookie──> Next.js ──转发──> FastAPI
                                                    │ get_current_user 依赖：
                                                    │   读 Cookie → 校验签名和过期时间 → 查用户
                                                    └─ 任一步失败 → 401
```

## 2. 关键设计决策

### 为什么 JWT 放在 httpOnly Cookie，而不是 localStorage？
- **localStorage：** 页面里的任何 JS 都能读取。一旦出现 XSS 漏洞（比如渲染了恶意内容），token 会被直接偷走。
- **httpOnly Cookie：** JS 完全读不到，浏览器在请求时自动携带。XSS 仍然可以冒充用户发请求，但拿不走 token。
- **代价：** Cookie 会自动携带，所以要防 CSRF。这里用 `SameSite=Lax`：其他网站发起的 POST 请求不会带上这个 Cookie。

### 为什么前端要通过 Next.js 转发（rewrites）访问后端？
浏览器只访问 `localhost:3000`，前后端对浏览器来说是**同源**的：
- Cookie 不需要设置跨域属性，`SameSite=Lax` 就够用
- 不需要配置 CORS
- 上线时只需要暴露一个域名

### 为什么密码用 argon2？
argon2 是密码哈希竞赛的冠军算法，计算时**故意占用大量内存**，GPU 和专用硬件很难并行暴力破解。每个密码自带随机盐，相同的密码哈希结果也不同。MD5、SHA256 这类通用哈希太快了，不适合存密码。

### 为什么"账号不存在"和"密码错误"返回一样的结果？
如果错误信息不同，攻击者就能逐个试邮箱，探测出哪些人注册过（用户枚举）。所以两种情况都返回 `401 邮箱或密码错误`。另外，账号不存在时也会做一次哈希计算，让两种情况的**响应时间**接近，防止通过耗时来区分。

### 为什么主键用 UUID 而不是自增整数？
自增 id 会暴露数据量（第 37 个用户），也方便攻击者按顺序猜别人的数据，例如 `/applications/38`。UUID 无法猜测。当然，真正的防线还是后端每次都校验数据归属（W2 开始会写越权测试）。

### 前端路由守卫（proxy.ts）只是"乐观检查"
`proxy.ts` 只看 Cookie **存不存在**，不校验签名。它的作用只是让未登录用户直接看到登录页，而不是先看到空白页面再跳转。**真正的鉴权永远在后端**：前端的任何检查都可以被绕过。

## 3. 踩过的坑

### 坑 1：Cookie 失效时卡在看板页
**现象：** Cookie 过期或被篡改后，访问 `/board` 会停在一个没有用户信息的页面上。

**原因：** 两个守卫互相打架：
1. 前端调用 `/me`，拿到 401，想跳转到 `/login`
2. `proxy.ts` 看到 Cookie **还在**，认为用户已登录，又把 `/login` 重定向回 `/board`

**解决：** 收到 401 时，先调用 `/api/auth/logout` 让后端清掉失效的 Cookie，再跳转登录页。

**教训：** 两层守卫的判断标准不一致（一个只看 Cookie 是否存在，一个校验 Cookie 内容）时，一定要考虑"Cookie 存在但无效"这种中间状态。

### 坑 2：Windows 上数据库连接卡住
**现象：** 测试一直挂起，没有任何报错。

**排查：** 用 `pytest -o faulthandler_timeout=12` 打印卡住时的调用栈，发现停在建立数据库连接这一步。再写脚本分别测试 `localhost`、`127.0.0.1`、`::1`：只有 IPv4 能连上。

**原因：** Windows 让 `localhost` 优先解析为 IPv6 的 `::1`，而 Docker Desktop 在这台机器上的 IPv6 端口转发连不通。

**解决：** 所有连接地址统一使用 `127.0.0.1`。

### 坑 3：PowerShell 写的 package.json 解析失败
Windows PowerShell 5 的 `Set-Content -Encoding utf8` 会在文件开头写入 BOM（`EF BB BF`），Node.js 解析 JSON 时会报错。之后写文件统一用不带 BOM 的 UTF-8。
