# AlphaJob 全栈学习路线

> 目标：项目里的每一行关键代码，你都能**讲清原理、独立修改、从零重写简化版**，面试时经得起追问。
>
> 这份路线配合 Claude 当助教使用。第一阶段（约 2 周）先学**线索 1：注册登录**和**线索 2：投递的增删改查**，这是全栈的基本功，后面的内容都建立在它们之上。

---

## 怎么学：每节课的五个步骤

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| ① 读设计笔记 | 先看 `docs/notes/` 里对应的笔记 | 先知道“为什么这样设计”，再看“怎么实现” |
| ② 带着问题读源码 | 按本文列出的顺序读文件，回答每课的问题 | 带着问题读，比从头到尾看有效得多 |
| ③ 听原理 | 看不懂的地方让 Claude 从原理讲起 | 补上“框架帮你做了什么”这一层 |
| ④ 动手练习 | 改功能 / 找 bug / 从零重写 | 看懂不等于会写，写过才算会 |
| ⑤ 讲给我听 | 用自己的话讲一遍，Claude 扮演面试官追问 | 讲不清楚的地方，就是还没懂的地方 |

### 和 Claude 配合的方式

直接对 Claude 说这些话就行：

| 你说 | Claude 会做什么 |
|---|---|
| “开始线索 1 第 1 课” | 带你过一遍这节课的阅读顺序，先提问再讲解 |
| “这段代码我看不懂：`文件:行号`” | 从原理讲起，必要时写一个最小示例 |
| “给我出一道找 bug 题” | 在练习分支里埋一个 bug，你来定位和修复 |
| “练习 X 做完了，帮我 review” | 像同事一样 review 你的代码，指出问题，但不直接改 |
| “模拟面试线索 1” | 扮演面试官连续追问，最后给反馈 |
| “给个提示” | 逐级给提示：方向 → 关键位置 → 接近答案，不直接给答案 |

### 练习的代码放哪里
- 每个练习新建一个分支，例如 `learn/jwt-from-scratch`，做完不一定要合并。
- 有价值的功能（比如练习 2.3 的“期望薪资”字段）review 通过后，可以正常提 PR 合并进 `main`。

## 学之前：准备工具（30 分钟）

1. 启动项目（命令见 [开发命令手册](开发命令手册.md)），确认能登录。
2. 学会用浏览器开发者工具（F12）：
   - **Network**：看每个请求的地址、方法、请求头、响应头、响应体
   - **Application → Cookies**：看 Cookie 的属性
   - **Console**：看前端报错
3. 打开后端接口文档 http://127.0.0.1:8000/api/docs ，点开任意接口，试着用 “Try it out” 调一次。

# 线索 1：注册登录（第 1 周）

**这条线索要搞懂的问题：**用户点了“登录”之后，从浏览器到数据库再回来，每一步发生了什么？服务器是怎么“记住”你已经登录了的？

**前置阅读：**[设计笔记 01：认证链路](notes/01-认证链路.md)

## 第 1 课：鸟瞰一个请求（第 1 天）

**目标：**不看代码，先用工具“看见”一次完整的登录。

**动手：**
1. 打开 Network 面板，退出登录后重新登录，找到 `login` 这个请求。
2. 记录下：请求地址、方法、请求体、响应状态码、响应头里的 `set-cookie`。
3. 在 Application → Cookies 里找到 `alphajob_token`，看它的 `HttpOnly`、`SameSite`、`Expires` 属性。
4. 刷新页面，看 `me` 请求的请求头里有没有自动带上这个 Cookie。

**回答这些问题：**
- 浏览器请求的是 `localhost:3000/api/auth/login`，可后端明明跑在 8000 端口。请求是怎么到后端的？（提示：看 [next.config.ts](../frontend/next.config.ts)）
- 为什么在 Console 里运行 `document.cookie` 看不到这个 token？
- 登录成功后，你什么都没做，为什么之后的请求都“自动”带上了身份？

**原理补充（让 Claude 讲）：**HTTP 是无状态的；Cookie 的工作机制；同源与跨域。

## 第 2 课：后端是怎么分层的（第 2 天）

**目标：**顺着一个请求，读懂后端的四层结构。

**阅读顺序：**
1. [backend/app/main.py](../backend/app/main.py)：应用是怎么组装起来的，路由挂在哪里
2. [backend/app/api/auth.py](../backend/app/api/auth.py)：**路由层**，只负责“收请求、回响应”
3. [backend/app/services/auth.py](../backend/app/services/auth.py)：**业务层**，规则写在这里
4. [backend/app/repositories/users.py](../backend/app/repositories/users.py)：**数据访问层**，只负责读写数据库
5. [backend/app/models/user.py](../backend/app/models/user.py) 和 [base.py](../backend/app/models/base.py)：**表结构**
6. [backend/app/schemas/auth.py](../backend/app/schemas/auth.py)：**请求和响应的数据格式**

**回答这些问题：**
- 注册时，邮箱已经被注册过，这个判断写在哪一层？为什么不写在路由层？
- `UserOut` 里为什么没有 `password_hash`？如果路由直接返回数据库对象，会发生什么？
- `repositories/users.py` 的 `create` 里用的是 `flush()` 而不是 `commit()`，提交是在哪里做的？为什么这样分工？
- 邮箱为什么要统一转成小写？在哪里转的？

**原理补充：**分层架构的意义；Pydantic 数据校验；ORM 是什么，它帮你省了什么、又隐藏了什么。

## 第 3 课：安全机制的原理（第 3 天）

**阅读顺序：**
1. [backend/app/core/security.py](../backend/app/core/security.py)：密码哈希、JWT 签发与校验
2. [backend/app/api/deps.py](../backend/app/api/deps.py)：`get_current_user` 是怎么从 Cookie 里认出“你是谁”的
3. [backend/app/api/auth.py](../backend/app/api/auth.py) 的 `_set_auth_cookie`：Cookie 的每个属性

**回答这些问题：**
- 数据库里存的不是密码，而是哈希值，那登录时是怎么比对的？
- 同一个密码哈希两次，结果为什么不一样？（提示：盐）
- JWT 的三段分别是什么？有人改了 payload 里的用户 id，服务器为什么能发现？
- `services/auth.py` 里那个 `_DUMMY_HASH` 是干什么的？去掉它会有什么安全问题？
- 登出只是删了 Cookie，那如果有人提前复制了这个 token，登出后还能用吗？怎么改进？

**原理补充：**哈希与加密的区别；为什么用 argon2 而不是 MD5；对称签名（HMAC）；XSS 和 CSRF 分别是什么，各用什么防。

## 第 4 课：前端这一侧（第 4 天）

**阅读顺序：**
1. [frontend/src/components/auth/auth-form.tsx](../frontend/src/components/auth/auth-form.tsx)：表单、校验、提交
2. [frontend/src/lib/api/client.ts](../frontend/src/lib/api/client.ts) 和 [auth.ts](../frontend/src/lib/api/auth.ts)：请求是怎么发出去的，错误是怎么处理的
3. [frontend/src/hooks/use-current-user.ts](../frontend/src/hooks/use-current-user.ts)：TanStack Query 怎么缓存“当前用户”
4. [frontend/src/proxy.ts](../frontend/src/proxy.ts)：路由守卫
5. [frontend/src/components/layout/app-shell.tsx](../frontend/src/components/layout/app-shell.tsx)：401 时的处理

**回答这些问题：**
- 密码少于 8 位时，前端和后端各校验了一次，为什么两边都要校验？
- `useMutation` 的 `onSuccess` 里为什么要 `setQueryData`？不写会怎样？
- `proxy.ts` 只检查 Cookie“存不存在”，不校验内容，为什么这样就够了？
- 设计笔记 01 里的“坑 1”（卡在看板页）是怎么产生的？用你自己的话讲一遍。

**原理补充：**React 组件与状态；受控表单；为什么要用 TanStack Query 管理“服务器数据”；`"use client"` 是什么意思。

## 第 5 课：测试与动手练习（第 5–7 天）

**先读：**[backend/tests/conftest.py](../backend/tests/conftest.py) 和 [test_auth.py](../backend/tests/test_auth.py)，弄懂测试数据库是怎么准备和清空的。

**练习（按难度排序，做完一个找 Claude review）：**

| 编号 | 类型 | 练习 | 考察点 |
|---|---|---|---|
| 1.1 | 观察 | 用接口文档或 `curl` 依次调用注册 → me → 登出 → me，观察每一步的状态码和 Cookie | HTTP、Cookie |
| 1.2 | 找 bug | 让 Claude 在认证代码里埋一个 bug，你用测试和日志找到它 | 读代码、调试 |
| 1.3 | 改功能 | 新增“修改昵称”：`PATCH /api/auth/me`，并在侧边栏点昵称就能修改 | 走一遍前后端全流程 |
| 1.4 | 写测试 | 给 1.3 写测试：正常修改、昵称过长、未登录 | 测试思维 |
| 1.5 | 从零重写 | **不用 PyJWT**，只用 Python 标准库（`hmac`、`hashlib`、`base64`、`json`）实现 `create_token` / `decode_token`，让现有的 `test_auth.py` 全部通过 | 真正理解 JWT |
| 1.6 | 进阶（可选） | 登录失败 5 次后锁定 15 分钟（用 Redis 计数） | Redis、防暴力破解 |

**结课：**对 Claude 说“模拟面试线索 1”。目标是能脱稿讲清下面这张图的每一步：

```
表单提交 → zod 校验 → fetch /api/auth/login → Next.js 代理到 8000
→ FastAPI 路由 → Pydantic 校验 → service: 查用户 + argon2 校验密码
→ 签发 JWT → Set-Cookie(HttpOnly, SameSite=Lax) → 前端缓存用户 → 跳转看板
→ 之后每个请求自动带 Cookie → get_current_user 解码 JWT → 查出用户
```

# 线索 2：投递的增删改查（第 2 周）

**这条线索要搞懂的问题：**一条数据从界面上的表单，到数据库里的一行，再显示回看板上，中间经过了什么？怎么保证用户 A 永远看不到用户 B 的数据？

**前置阅读：**[设计笔记 02](notes/02-求职看板与大模型抽象层.md) 第 1、2 节（数据模型、拖拽排序）

## 第 1 课：数据库与数据模型（第 1 天）

**阅读顺序：**
1. [backend/app/models/application.py](../backend/app/models/application.py)：投递和日程两张表
2. [backend/alembic/versions/](../backend/alembic/versions/) 里的第二个迁移文件：模型是怎么变成建表 SQL 的

**动手：**进数据库看看真实的表（命令见[开发命令手册](开发命令手册.md)第 5 节）：
```sql
\d applications
SELECT company, role, stage, position FROM applications;
```

**回答这些问题：**
- `user_id` 的外键为什么要设 `ondelete="CASCADE"`？
- `stage` 为什么存成 varchar，而不是 PostgreSQL 原生的 ENUM？
- `Event` 表里为什么又冗余存了一份 `user_id`？这么做的代价是什么？
- `jd_parsed` 为什么用 JSONB，而不是拆成多张表？
- 迁移（migration）解决的是什么问题？如果不用 Alembic，团队里每个人的数据库会出现什么情况？

**原理补充：**主键、外键、索引；一对多关系；JSONB 的适用场景；数据库迁移。

## 第 2 课：增删改查的后端（第 2 天）

**阅读顺序：**
1. [backend/app/schemas/application.py](../backend/app/schemas/application.py)：注意 `ApplicationCreate` 和 `ApplicationUpdate` 的区别
2. [backend/app/api/applications.py](../backend/app/api/applications.py)：5 个接口分别对应什么 HTTP 方法
3. [backend/app/services/applications.py](../backend/app/services/applications.py)：业务规则
4. [backend/app/repositories/applications.py](../backend/app/repositories/applications.py)：**每个查询都带 `user_id`**

**动手：**临时打开 SQL 日志，看 ORM 实际生成了什么 SQL。在 [backend/app/core/db.py](../backend/app/core/db.py) 里给 `create_async_engine(...)` 加上 `echo=True`，然后新建一条投递，看后端终端打印出的 SQL。**看完记得改回去。**

**回答这些问题：**
- 为什么更新用 `PATCH` 而不是 `PUT`？`exclude_unset=True` 起了什么作用？
- 从“待投递”拖到“已投递”时，`applied_at` 是在哪里被自动填上的？
- 访问别人的投递，返回的是 404 而不是 403。为什么？
- `next_events` 里用了 `DISTINCT ON`，它解决了什么问题？什么是“N+1 查询”？
- 删除投递时，它的日程是怎么一起被删掉的？

**原理补充：**REST 的资源与方法；幂等性；SQL 的 JOIN、DISTINCT ON；N+1 问题。

## 第 3 课：增删改查的前端（第 3 天）

**阅读顺序：**
1. [frontend/src/lib/api/applications.ts](../frontend/src/lib/api/applications.ts)：类型从哪里来（`schema.d.ts` 是怎么生成的？看 `package.json` 里的 `gen:api`）
2. [frontend/src/hooks/use-applications.ts](../frontend/src/hooks/use-applications.ts)：查询、修改、**乐观更新**
3. [frontend/src/components/applications/new-application-dialog.tsx](../frontend/src/components/applications/new-application-dialog.tsx)：两步式表单
4. [frontend/src/components/board/board.tsx](../frontend/src/components/board/board.tsx)：拖拽和 `positionBetween`

**动手：**
- 在 Network 面板把网络设成 **Offline**，然后拖一张卡片，观察它先移过去、再弹回来的过程。这就是乐观更新加失败回滚。
- 后端改一个字段名（比如把 `company` 改成 `company_name`），运行 `pnpm gen:api`，再运行 `pnpm typecheck`，看前端哪些地方报错。**看完记得改回去。**

**回答这些问题：**
- `queryKey` 有什么用？新建投递后，看板是怎么知道要刷新的？
- 乐观更新的三个回调 `onMutate` / `onError` / `onSettled` 各做了什么？
- 拖到两张卡片中间时，新 position 是怎么算出来的？为什么用浮点数？
- 为什么前端类型要从后端自动生成，而不是手写？

## 第 4 课：测试与动手练习（第 4–7 天）

**先读：**[backend/tests/test_applications.py](../backend/tests/test_applications.py)，重点看 `test_users_cannot_access_each_other`。

**练习：**

| 编号 | 类型 | 练习 | 考察点 |
|---|---|---|---|

| 2.2 | 改功能 | 在看板顶部加一个搜索框，按公司或岗位过滤（后端的 `q` 参数已经支持了，只需要做前端） | 查询参数、queryKey |
