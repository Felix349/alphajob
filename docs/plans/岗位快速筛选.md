# 岗位快速筛选（设计稿）

> 状态：P1 后端流水线、P2 前端页面已完成（见文末“实施记录”）；P3 浏览器插件待开始。

## 1. 要解决的问题

一家大厂的校招页动辄几十到几百个岗位，逐个点开看 JD、对照简历，一家公司就要花掉大半天。

**目标：迅速缩小投递范围。**用户在浏览器里打开某家公司的招聘页，点一下插件，几分钟后拿到一份“最适合你的前几个岗位”清单：每个岗位有匹配度、主要优势、主要差距和原链接，勾选后可以一键加入投递记录。

**明确不做：**
- 自动投递：投递不可逆，网申表单差异大，最终由用户自己在招聘网站上完成
- 后台批量爬取：只读取用户当前打开、主动触发的页面

## 2. 整体流程

```
浏览器插件                         AlphaJob 后端                         AlphaJob 页面
──────────                         ─────────────                         ────────────
① 用户在招聘列表页点“读取”
   抓取页面上的岗位（标题、地点、
   类别、链接、摘要）──────────────> ② 建一个“筛选批次”，存下岗位列表
                                     ③ 硬条件过滤（城市、校招/实习…）
                                     ④ 粗筛：从几百个里挑出前 N 个
                    <────────────── 返回需要详情的 N 个岗位链接
⑤ 逐个打开详情页（限速），
   取回 JD 正文 ───────────────────> ⑥ 精排：逐条对照简历，按规则计分
                                     ⑦ 排序，生成推荐清单 ──────────────> ⑧ 推荐清单
                                                                          勾选 → 一键加入投递记录
                                                                          （进入“想投”，自动解析 JD）
```

关键设计：**两级筛选**。列表页通常只有岗位名和地点，读取详情要逐个打开页面、精排要调用大模型，都很慢。所以先用便宜的方法把几百个缩到 N 个（默认 15），只对这 N 个取详情、做精排。这和 RAG 的“召回 + 重排”是同一个思路。

## 3. 浏览器插件

- **Chrome 扩展（Manifest V3）**，放在仓库的 `extension/` 目录，以“开发者模式加载已解压的扩展”的方式使用，不上架商店。
- **读取列表页**：内容脚本把页面上的岗位卡片抽取成 `{title, location, category, url, snippet}`。
  - 优先用针对常见招聘系统的规则抽取（例如 Moka、北森、飞书招聘，它们的页面结构固定）。
  - 不认识的页面：把页面的可见文本和链接发给后端，由大模型抽取岗位列表（一次调用，低成本）。
  - 只读取当前已加载的内容。列表分页或需要“加载更多”时，用户翻页后再点一次“读取”，追加到同一个批次。
- **读取详情页**：在用户的浏览器里逐个请求后端返回的 N 个详情链接，**每个间隔约 2 秒**，取回正文后提交给后端。在用户自己的浏览器里读取，能看到用户能看到的页面，也不涉及绕过登录或验证码。
- **和后端的认证**：插件发起的请求属于跨站请求，浏览器不会带上 AlphaJob 的登录 Cookie（SameSite）。所以在 AlphaJob 的设置页生成一个**插件专用令牌**，填进插件设置。令牌只能调用筛选相关的接口，可以随时撤销。

## 4. 后端

### 4.1 数据

| 表 | 内容 |
|---|---|
| `screening_batches` | 一次筛选：公司名、来源页面、筛选条件、使用的简历语言、状态（读取中 / 粗筛完成 / 精排中 / 完成） |
| `screening_jobs` | 批次里的岗位：标题、地点、类别、链接、摘要、JD 正文（精排的才有）、粗筛结果、精排结果、是否已加入投递 |
| `extension_tokens` | 插件令牌（只存哈希）、创建时间、最近使用时间 |

同一批次里，按链接去重，翻页重复读取不会产生重复岗位。

### 4.2 硬条件过滤（不调用模型）

用户在插件或页面上设置：城市、招聘类型（校招 / 实习 / 社招）、排除关键词（如“销售”“客服”）。直接按字段和关键词过滤。

### 4.3 粗筛：几百个 → N 个

**列表页大多只有岗位名、地点、类别，没有 JD 正文**，这决定了粗筛的做法：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 大模型批量判断（**推荐**） | 把简历摘要和全部岗位名一起发给模型，每个岗位给出相关度 0–3 分和一句理由。岗位名很短，200 个岗位约 4–6 千 tokens，分 1–3 次调用 | 能理解“AI 应用工程师”和“大模型算法”的差别，也能识别“产品经理”这类方向不对的岗位 | 每批几分钱；结果有一定随机性 |
| B. 向量相似度 | 简历和岗位名分别向量化，按余弦相似度排序（可用阿里云百炼的文本向量模型，已有 Key） | 几乎免费、结果稳定 | 只有岗位名时效果差：“后端开发”和“Agent 开发”的向量可能很接近 |

推荐 MVP 用 A，同时把 B 做成可选，用评测集（第 6 节）对比两者的召回率，用数据决定最终方案。列表页带有较长摘要时，B 的效果会好很多。

### 4.4 精排：N 个 → 推荐清单

对 N 个岗位逐个调用大模型，判断简历与 JD 的匹配情况，**复用现有的“规则计分”**：模型逐条判断要求的匹配程度（strong / partial / missing）和是否必备，程序加权算出匹配度。

但不直接复用完整的匹配分析：它还要生成备考清单、简历修改建议和面试题，一次约 45 秒、7 千多 tokens，15 个岗位就要十几分钟。精排用一个**精简版输出**：

- 逐条对照（只要 requirement、importance、level，依据压缩到一句话）
- 一句话总结：最大的优势、最大的差距

预计每个岗位 10–15 秒，4 个并发时，15 个岗位约 1 分钟。用户选中岗位、加入投递记录之后，再按需跑完整的匹配分析。

### 4.5 推荐清单

按匹配度排序，并列时必备要求缺失少的排前面。每项显示：岗位名、地点、匹配度、优势、差距、原链接、“加入投递记录”按钮。

加入投递记录：新建一条“想投”阶段的投递，填入公司、岗位、地点、链接和 JD 正文，自动触发 JD 解析。

## 5. 前端页面

- **新页面“岗位筛选”**：筛选批次列表；每个批次显示进度（读取 → 粗筛 → 精排），完成后显示推荐清单。精排过程用 SSE 推送进度，逐个岗位出结果。
- **设置页**：生成和撤销插件令牌。
- **插件弹窗**：读取当前页面、显示已读取的岗位数、设置硬条件、开始筛选、打开 AlphaJob 查看结果。

## 6. 评测

和匹配分析一样，先有评测，才知道改得好不好：

- **标注**：选 3–5 家公司的真实列表页，由你标注哪些岗位“值得投”，作为标准答案（只存在本地，不进仓库）。
- **粗筛**：计算召回率，即标准答案里有多少进入了前 N 个。目标是前 15 个的召回率 ≥ 90%。粗筛漏掉的岗位，后面的步骤再准也找不回来。
- **精排**：看前 5 个里有多少是标准答案（Precision@5），以及排序是否合理。
- **成本和耗时**：每个批次的 tokens 和总耗时。

## 7. 合规与隐私

- 只读取用户当前打开的页面和用户触发的详情页，限速，不做后台批量抓取。
- 不绕过登录、验证码和反爬机制；遇到这类页面，提示用户手动复制 JD。
- 读取到的岗位只存在用户本地的 AlphaJob 数据库。
- 插件令牌只存哈希，只能访问筛选相关接口，可随时撤销。

## 10. 实施记录

### P1 后端流水线（2026-11-17）

**接口**（前缀 `/api/screening`）：

| 接口 | 作用 |
|---|---|
| `POST /batches` · `GET /batches` · `GET/DELETE /batches/{id}` | 批次的增删查；详情里的岗位已按推荐顺序排好 |
| `POST /batches/{id}/jobs` | 提交结构化的岗位列表（给插件用），按链接或“岗位名 + 地点”去重 |
| `POST /batches/{id}/extract` | 从粘贴的列表页文本里抽取岗位（按行切成约 1.2 万字一段，逐段调用模型） |
| `POST /batches/{id}/screen` | 硬条件过滤 + 粗筛，返回进入精排、但还缺 JD 的岗位 |
| `PUT /jobs/{id}/jd` | 补充 JD 正文；JD 变了，之前的精排结果作废 |
| `POST /batches/{id}/rank` | 精排（SSE）：start → 每完成一个推送 job → done |
| `POST /jobs/{id}/import` | 加入投递记录（“想投”）；顺便解析 JD；重复调用返回同一条 |

**实现上的几个决定：**
- **粗筛宁可多留**：模型漏判的岗位按 2 分保留；提示词也要求“看不准时给 2 分”。粗筛漏掉的岗位，后面再准也找不回来。
- **精排复用规则计分**：`compute_score` 改为只依赖 `importance` 和 `level` 两个字段，完整匹配分析和精排共用同一套规则。
- **精排用温度 0**（effort="low"）：排序需要稳定，同样的输入尽量给出同样的判断。
- **精排并发 4 个，每个岗位单独开数据库会话**：一个会话不能被多个并发任务同时使用。一个岗位失败只记录原因，不影响其他岗位。
- **选简历的规则和匹配分析一致**：指定了就用指定的，否则按岗位文本的语言选（`pick_resume`）。
- **加入投递记录不依赖 AI**：没配 API Key 时照常创建，只是不解析 JD。

**测试**：13 个自动化测试（抽取与去重、越权访问、硬条件过滤、粗筛漏判、精排计分与排序、单个失败不影响其他、JD 变更作废结果、加入投递记录的幂等性、无 AI 时可用）。后端共 139 个测试通过。

**真实数据试跑**（华为 18 个真实岗位 × 自己的简历，deepseek-flash，精排前 5 个）：

| 步骤 | 耗时 | 结果 |
|---|---|---|
| 抽取 | 3 秒 | 18 个岗位全部识别，导航栏、页脚没有混入 |
| 粗筛 | 2 秒 | Agent 工程师、后训练与强化学习、语言大模型给 3 分；搜索推荐、多模态、空间智能等给 1 分，理由都能对上简历 |
| 精排 | 4 秒（5 个） | AI 技术应用 92、Agent 工程师 73、语言大模型 67、后训练与强化学习 61、AI 数据系统 59 |

**发现的问题（留给 P4）：**

1. **同分岗位的取舍**：粗筛有 7 个岗位同为 2 分，精排只取 5 个时，同分岗位按页面顺序取舍，AI 模型评测、AI 算法、AI 训推被挤掉了。0–3 分的刻度对“要不要细看”足够，但对“同分时谁先”区分不出来。可选的改进：增加刻度、同分时用向量相似度排序，或默认精排数量足够大（默认 15 时这次不会出现）。

### P2 前端页面（2026-11-17）

- 侧边栏新增“岗位筛选”。列表页显示各批次的进度；“新建筛选”对话框设置公司、来源链接、城市、招聘类型、排除关键词、精排数量、使用的简历。
- 批次详情页按步骤展开：① 读取岗位（粘贴列表页内容，可追加）→ ② 粗筛 → 补充 JD（每个缺 JD 的入选岗位有原页面链接和输入框）→ ③ 精排（SSE 进度条，每完成一个岗位，推荐清单里就出现一个分数）。
- 推荐清单：排名、匹配度、优势、差距，可展开逐条对照，一键加入投递记录（之后显示“已加入，查看”）。
- 底部可折叠的“其他岗位”：被排除的原因或粗筛的分数和理由，方便检查 AI 有没有漏掉合适的岗位。

**浏览器实测**（华为批次）：列表、详情、逐条对照、重新精排的进度条、其他岗位、新建对话框都正常，控制台无报错。修了一个窄屏下的排版问题：原来“加入投递记录”按钮单独占一列，窄屏时把正文挤成一字一行；改为和标题同一行、空间不够时换行。

2. **精排结果不稳定**（P2 实测时发现）：同样的输入、温度为 0，两次精排的分数仍有差异：AI 技术应用 92 → 86，后训练与强化学习 61 → 71，AI 数据系统 59 → 54，第 3、4 名互换。DeepSeek 先“思考”再输出，温度压不住思考过程的随机性。对“排序”影响较大，可选的改进：多次判断取平均、只在分数差距明显时区分先后（如显示为“同一档”），或换用不带思考的模型做精排。
